# ISMS-P Dynamic Audit Assurance — UX Document

## 1. 왜 "Dynamic Audit Assurance"인가

기존 GRC 대시보드는 "점수가 몇 점인가"를 보여준다. 심사 대응에서 실제로 필요한 질문은 다르다:

- 심사원이 **지금** 이 질문을 하면 무엇을 보여줄 수 있는가?
- 이 증적은 **어느 모집단**의 표본인가?
- 정책 문서와 실제 시스템 설정이 **어긋나는 지점**은 어디인가?
- 지적사항이 **종결되려면** 무엇이 남았는가?

이 제품은 정적 점수판이 아니라 **심사 대응 작업 공간**이다. 모든 수치는 클릭 가능하고,
클릭은 항상 "근거가 있는 다음 화면"으로 연결된다.

## 2. 정보 구조 — 왜 Timeline이 주 구조가 아닌가

Audit Time Machine은 강력한 보조 장치지만, 기본 IA를 시계열로 만들면
"현재 무엇을 해야 하는가"가 흐려진다. 그래서:

- **주 구조**: 계층적 컨텍스트 (심사 → 영역 → 통제 → 증적 → 지적 → 조치)
- **보조 구조**: Timeline — 선택한 시점으로 전체 화면 상태를 재구성

시간은 "필터"가 아니라 "차원"이다. 슬라이더를 움직이면 KPI·통제 상태·지적사항이
그 시점의 스냅샷으로 바뀌어, **무엇이 개선되었는가**를 시각적으로 보여준다.

## 3. 핵심 흐름의 표현 — Control → Evidence → GAP → Finding → Action → Verification

이 흐름은 두 수준으로 구현된다.

**통제 상세 워크스페이스 (`/controls/{id}`)** — 9개 노드 체인:
```
Requirement → Policy → System Configuration → Population → Evidence
           → Validation → Finding → Action → Verification
```
각 노드는 클릭 가능하며, 실제 데이터(정책 문서 버전, 설정 관측값, 모집단 크기,
원장 레코드 해시, 연결된 지적사항)를 인라인으로 펼쳐 보여준다.

**화면 간 이동** — 모든 지표는 출발점이다:
- KPI `준비도 84%` → `/controls?state=READY` (READY 통제만 강조)
- KPI `GAP 21` → `/gap` (필터 유지)
- GAP 행 클릭 → `/controls/{id}` (해당 통제 컨텍스트)
- 지적사항 카드 → 생명주기 단계 시각화 + 보완조치 상태

컨텍스트(audit, control, date, 필터)는 쿼리 파라미터로 보존되어
뒤로 가기·공유·새로고침에서 유실되지 않는다.

## 4. Audit Time Machine

`/audit` 상단의 타임라인 컨트롤. 90/60/30일 전·오늘 스냅샷을 선택하면:

- 준비도·증적율·GAP 수·미해결 지적사항이 그 시점 값으로 변경
- 변경된 통제 상태 목록 표시 (예: 2.6.3 MISSING→PARTIAL)
- 통제 링크는 해당 시점 컨텍스트를 유지한 채 상세로 이동

현재는 결정론적 합성 스냅샷(demo:true). 실제 구현 시 증적 원장의
시스템 타임스탬프가 스냅샷의 데이터 소스가 된다 — 과거 상태를
"재구성"할 수 있는 것은 원장이 append-only이기 때문이다.

## 5. Audit Replay

심사원 질의를 스크립트로 리허설한다. 퇴직자 계정 시나리오:

```
심사원 질의 → HR 모집단 조회 → IAM 모집단 조회 → 교차 대사
→ 예외 탐지(계정 잔존 4건) → 증적 제시(해시체인 검증) → 후속 질의 예측
```

재생/일시정지/이전/다음/처음부터/단계 점프를 지원하고,
각 단계에서 증적·지적사항으로 바로 점프할 수 있다.
자율 AI는 사용하지 않는다 — 목적은 "심사원이 볼 것"의 사전 검증이다.

## 6. AI 경계

AI 심사지원 에이전트는 다음만 한다: 요약, 설명, 검색, 후속 질의 제안,
응답 초안 작성. 다음은 절대 하지 않는다: 공식 판정, 지적사항 종결,
증적 승인, 평가 변경, 증적 날조. 모든 응답에 advisory 배너가 표시된다.

## 7. 상태 의미론 — 색상만으로 표현하지 않음

| 상태 | 색 | 라벨 |
|------|-----|------|
| READY/Available | 초록 | 준비완료/확보 |
| PARTIAL | 황색 | 일부충족 |
| MISSING/Expired | 적색 | 미충족/만료 |
| CONFLICT | 보라 | 정책↔실제 불일치 |
| Awaiting Review | 보라 | 검토 대기 |

모든 배지는 아이콘(점)+텍스트 라벨을 함께 사용한다.
"미확인"은 "합격"으로 위장하지 않는다 — 데이터가 없으면 Missing으로 명시한다.

## 8. 데모 데이터 경계

모든 합성 데이터는 `demo: true`로 마킹되고 UI에 "데모 데이터" 배지가 표시된다.
백엔드 엔진 결과(원장 해시체인, 정합성 결과, 지적사항 생명주기)는 실제 엔진 객체를
사용하며, 합성이 필요한 부분(타임라인, 리플레이, 활동 스트림, 어시스턴트)만
결정론적 mock으로 제공한다. 프로덕션 전환 시 `/api/audit/*` 계약만 실제
구현으로 교체하면 UI는 그대로 동작한다.
